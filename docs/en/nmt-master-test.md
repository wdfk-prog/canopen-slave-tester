# NMT master validation

NMT-master validation reverses the normal Host/DUT relationship. The Linux application is compiled as `CANOPEN_ROLE_SLAVE` and creates a Lely `BasicSlave` on Node-ID 2. The MCU under test must act as the NMT master and drive the peer through the expected state transitions.

## Enable

Set the Host role and validation switch before rebuilding:

```c
#define CANOPEN_ROLE CANOPEN_ROLE_SLAVE
#define CANOPEN_ENABLE_NMT_MASTER_PROCESS 1
```

The switch lives in `include/nmt_master_process.h`; the role is selected in `include/canopen_config.h`.

## What the Host observes

The peer registers Lely NMT callbacks and verifies the state sequence generated by external NMT commands. The DUT initiates the test; the Linux peer does not use SDO or a generic raw-CAN injection path to fake MCU NMT-master behavior.

The current implementation also uses the configured producer heartbeat for the software peer so the MCU can supervise Node 2 during the sequence.

## Evidence boundary

A Lely `BasicSlave` callback proves that the peer protocol stack accepted the received NMT command and entered the associated state transition path. Complete target acceptance should still correlate:

- MCU-side NMT-master action/logs;
- Host callback order and timeout results;
- CAN trace of the actual NMT frames;
- heartbeat continuity after the final Operational state.
